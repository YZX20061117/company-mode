# 5 层死循环防护（v3.0 增强）

## 设计目标

防止 Agent 在讨论/决策/施工中陷入无效循环，白白消耗 Token。

## Layer 1: 辩论轮次上限

- 触发对象：CEO-DA 辩论
- 规则：每个决策点最多辩论 3 轮
- 超限行为：自动终止辩论，CEO 做出最终裁定；如 CEO 也无法裁决，提交用户仲裁
- 计数器：每个决策独立计数，不跨决策累计

## Layer 2: 决策数量上限

- 触发对象：每个 Phase 内的重大决策
- 规则：Align 最多 5 个重大决策点；Build 不限（施工中技术决策是正常的）
- 超限行为：CEO 必须合并或简化决策点，优先解决核心问题

## Layer 3: 动态 Token 预算 + 熔断器

### 3A: 分阶段预算（v3.0 调整）

| Phase | Token 预算 | 80% 警告 | 100% 硬停 |
|-------|----------|---------|----------|
| Align | 40K | 32K | 停，汇报对齐结论 |
| Build | 150K | 120K | 停，汇报完成和未完成项 |
| Verify | 20K | 16K | 停，汇报审计结论 |

施工队（OpenCode/Codex）消耗不入主线程预算。

### 3B: 80% 自动降级

- 触发：当前 Phase Token 消耗达预算 80%
- 动作：
  1. CEO 自动切换到低价模型（如 `claude-haiku` 或 `deepseek-chat`）完成剩余讨论
  2. 向用户报告："Phase X 预算已用 80%，已切换到低价模型"
  3. DA 审查保持模型不变（安全审查不降级）
- 例外：安全审查、CSO 审计不执行降级

### 3C: 按角色熔断

| 熔断条件 | 触发 | 动作 |
|---------|------|------|
| 单 Agent 超 2 倍预期 Token | Agent 调用返回 | 终止该 Agent，CEO 接管其产出并标注"Agent 超预算" |
| DA 辩论超 5 轮（含重试） | 第 5 轮结束 | 强制终止辩论，提交用户仲裁 |
| 施工队 3 次连续失败 | 第 3 次失败 | 停止施工队，CEO 评估是否兜底或标记为阻塞 |
| 同一文件被编辑超 10 次 | 第 10 次编辑 | 暂停施工，DA 审查是否有方向性错误 |

### 3D: 100% 硬停

- 触发：消耗达预算 100%
- 动作：立即停止当前 Phase，向用户汇报已完成和未完成项，由用户决定是否追加预算

## Layer 4: 状态哈希循环检测

- 触发对象：连续多轮讨论
- 规则：每轮辩论提取 State 哈希指纹，与历史 5 轮比对，精确检测循环
- 检测方法：
  1. 每轮辩论结束后，CEO 提取状态指纹：
     ```
     State = hash(决策点 ID + 各方立场摘要 + 结论摘要 + 新论据摘要)
     ```
  2. 存入滑动窗口（保留最近 5 轮）
  3. 当前 State 与历史任一相同 → **判定为循环**
  4. 最近 3 轮结论实质相同但表述不同 → 警告疑似循环
- 超限行为：
  - 哈希碰撞：立即跳出，向用户汇报循环情况
  - 疑似循环：提醒用户后继续 1 轮，无新论据则终止

## Layer 4.5: Self-Healing 失败分类（v3.0 新增）

- 触发对象：Build 阶段 Self-Healing 循环
- 规则：施工失败后，DA 分析并分类失败原因（而非笼统说"失败"）

### 失败分类

| 类别 | 判断依据 | 应对策略 | 后续动作 |
|------|---------|---------|---------|
| **规格模糊** | 测试失败但实现逻辑自洽；多个合理实现都通不过测试 | 通知 CTO 澄清架构规格 | 更新 architecture-brief.md |
| **实现复杂** | 单 Task 代码量超预期 >2 倍；跨多个不相关的模块 | 通知 PM 拆分 Task | 更新 task-tree.md |
| **工具限制** | 施工工具无法完成特定操作；不是代码逻辑问题 | 切换施工工具（OpenCode ↔ Codex） | 记录工具能力边界 |
| **模型能力** | 逻辑正确但语法/API 使用错误；反复出现低级错误 | 升级模型或标记降级事件 | 记录模型能力边界 |

### Self-Healing 循环规则

```
施工完成 → 测试
  ├── 全部通过 → 进入审查
  └── 有失败 → DA 分析（交叉模型）→ 失败分类
                  → CEO 按分类生成修复指令
                  → 施工队执行修复
                  → 重新测试
                  ├── 通过 → 进入审查
                  └── 仍失败 → 重复（最多 3 轮）
                              ├── 第 2 轮：DA 验证修复方向是否正确
                              └── 第 3 轮仍失败 → 标记阻塞 + 失败分类 + 已尝试方案
                                                  → CEO 向用户汇报
```

### 与 Layer 4 的协作

- Layer 4 检测**辩论循环**（CEO-DA 讨论是否进入死循环）
- Layer 4.5 分类**施工失败**（Self-Healing 为什么不能自动修复）
- 如果同一 Task 的失败分类连续 2 轮相同 → Layer 4 的哈希检测会在第 3 轮启动前触发 → 提前终止循环

## Layer 5: 用户逃生舱

- 触发对象：任何时刻
- 规则：用户说以下任意关键词即触发：
  - "跳过" / "skip" → 跳过当前讨论，保持默认选择
  - "继续" / "continue" → 终止当前讨论，采纳当前倾向
  - "我来定" / "I decide" → 提交当前选项让用户决策
  - "停" / "stop" / "abort" → 紧急停止，保存状态
- 触发后行为：立即执行用户指令，不做任何额外讨论

## 实施方式

- Layer 1-3 由 CEO 在每个 Phase 开始前设定计数器
- Layer 4 由 CEO 在每轮辩论结束时手算状态摘要
- Layer 4.5 由 DA 在 Self-Healing 失败时执行分类
- Layer 5 全程待命，无条件响应

## 其他防浪费措施

1. CEO 发现讨论进入"形而上学"领域 → 立即拉回
2. 任何讨论超过 5 分钟没有进展 → CEO 提议搁置
3. DA 质疑如果没有具体论据支撑 → CEO 要求补充论据
4. 纯偏好问题 → 不经过 DA，CEO 直接决定
5. **v3.0 新增**：DA 不在低风险代码上触发 → Fast Path 跳过低成本审查
