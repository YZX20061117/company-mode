# L5: 架构设计——怎么拆分系统

> 阶段：2（伴随Phase 3-4）
> 目标：理解系统拆分的核心原则

## 1. 架构是什么

**本质**：架构 = 决定哪些东西放在一起，哪些东西分开。

**不是**：画一堆花哨的图

**是**：做一组不可逆的决策。（代码可以重构，但架构方向选错了，代价极大）

## 2. 三个核心原则

### 2.1 高内聚，低耦合

- **内聚**：一个模块内部的东西应该一起变化
- **耦合**：模块之间的依赖越少越好

**检验方法**：如果要改一个功能，你需要改几个文件？1-2个文件 = 好架构，5+个文件 = 需要重构

### 2.2 接口先行

先定义模块之间怎么通信（接口），再实现内部逻辑。

```
API定义（接口/契约）→ 模块实现 → 集成
```

**在Company Mode中**：Phase 1-2先定义接口，Phase 5才写代码，就是这个原因。

### 2.3 关注点分离

不同类型的逻辑不要混在一起：
- 业务逻辑 ≠ 数据访问逻辑
- UI逻辑 ≠ 状态管理
- 认证逻辑 ≠ 业务逻辑

**反例**：在React组件里直接写SQL查询
**正例**：组件 → API调用 → Service层 → 数据库

## 3. 常见架构模式

| 模式 | 适合场景 | Company Mode例子 |
|------|---------|-----------------|
| 分层架构 | Web应用 | Express → Service → Repository |
| 微服务 | 大团队、独立部署 | 不适用（我们是小项目） |
| 模块化单体 | 小团队、快速迭代 | **推荐首选** |

## 4. 数据流设计

设计数据流时问三个问题：
1. 数据从哪里进来的？
2. 经过哪些变换？
3. 最终存到哪里/显示在哪里？

## 5. 技术选型框架

| 问题 | 思考 |
|------|------|
| 团队熟悉度 | 有人会用吗？ |
| 生态成熟度 | 有问题能找到答案吗？ |
| 许可 | 开源协议允许商用吗？ |
| 维护状态 | 最近在更新吗？ |
| 性能 | 能满足项目的量级吗？ |

**最重要的原则**：不确定时选最成熟的那个，不选最新的。
